## Introduction

This is the specification for the `ballerina/dataservice` package of the [Ballerina language](https://ballerina.io/). The package holds the annotations that select what a data service generated by `bal persist` exposes, and the protocol-neutral runtime that generated services call. How the persist tool generates a service is specified in the [persist tool specification](https://github.com/ballerina-platform/persist-tools/blob/main/docs/spec/spec.md#9-data-service-generation), and each protocol package, such as `ballerina/dataservice.http`, has its own specification.

The conforming implementation of the specification is released and included in the distribution. Any deviation from the specification is considered a bug.

### Notation

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY and OPTIONAL are interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174) when, and only when, they appear in all capitals. Sentences that state behaviour in the present tense are also normative. The overview, notes and examples are informative.

## 1. Overview

A persist model describes entities as Ballerina record types. Annotating an entity with `@dataservice:Expose` makes `bal persist` generate a data service that offers create, read, update and delete operations on it over a protocol, with no hand-written service code. Field rules on the model's fields say which fields a caller sees and writes.

The generated service is plain Ballerina code. It calls the functions of this package for the behaviour that every protocol shares: the error body and its codes, the mapping of persist errors to it, the string forms of dates, times and bytes, the page sizes, and the SQL clauses of a read. A protocol package adds what is specific to its protocol, such as HTTP status codes.

The functions that generated code calls are a stable API. New behaviour is added through new functions or optional parameters.

## 2. Terminology

- **Entity:** a record type of a persist model.
- **Exposed entity:** an entity with the `@dataservice:Expose` annotation.
- **Action:** one of `read`, `create`, `update` and `delete`, the unit that `@dataservice:Expose` allows and that auth scopes apply to.
- **Operation:** a request that a data service handles: get many, get one, get related, create one, create many, patch one and delete one.
- **Key:** the values of an entity's key fields, its `readonly` fields, in declaration order. A composite key has more than one value.
- **Key text:** each value of a key written with `toString`, joined by `/` in key order. The composite key `["P1", 1]` has the key text `P1/1`, `1.5` stays `1.5`, and a `decimal` keeps its scale.
- **Error body:** the record that a data service answers every error with, holding a `code` and a `message`.
- **Wire type:** a type that a protocol generates in place of a persist type, holding dates, times and `byte[]` values as strings.
- **Entity description:** the value of type `Entity` that a generated service holds for each exposed entity, from which this package writes queries.
- **Relation:** a pair of relation fields that link two entities. The side that holds the foreign key is the owning side. A relation is to-many in a direction whose relation field is an array, and to-one otherwise.
- **Link:** the fields that a relation matches on: the foreign key fields and the related entity's key on the owning side, and the key and the related entity's foreign key fields on the other side.

## 3. Exposing entities

### 3.1. Description

The `@dataservice:Expose` annotation selects the entities of a persist model that a data service exposes, the actions each allows, and the scopes each action requires with auth.

### 3.2. Configuration

`Expose` is a constant annotation on a type definition, of type `ExposeConfig`.

| Field | Type | Default | Meaning |
|---|---|---|---|
| `operations` | `[Operation, Operation...]` | `[READ, CREATE, UPDATE, DELETE]` | The actions the entity allows. An operation is written as an `Operation` member, such as `dataservice:READ`, or as its string value, such as `"read"`. The type requires at least one action. |
| `scopes` | `Scopes` | absent | The scopes of each action, used only when the persist tool option `options.dataservice.auth` is `true`. `Scopes` has the optional fields `read`, `create`, `update` and `delete`, each a `string[]`. |

### 3.3. Behaviour

1. An entity is exposed only when its record type has `@dataservice:Expose`. An entity without it has no operations.
2. An exposed entity allows the actions in `operations`. Each action enables these operations:

   | Action | Operations |
   |---|---|
   | `read` | Get many, get one, get related |
   | `create` | Create one, create many |
   | `update` | Patch one |
   | `delete` | Delete one |

3. With auth, a caller needs any one scope of an action's list in `scopes`. An empty list requires only an authenticated caller. An action not listed requires the scope `<resource>:<action>`, where `<resource>` is the entity's persist resource name, such as `employees:read`.
4. Without auth, no scope is checked and `scopes` has no effect.
5. The annotation's value is evaluated at compile time and is not kept at runtime.
6. Whether a data service is generated is decided by `options.dataservice` in the `[[tool.persist]]` entry of `Ballerina.toml`. The annotations only select what the service exposes.

For example, `@dataservice:Expose {operations: [dataservice:READ, dataservice:UPDATE]}` exposes get many, get one, get related and patch one, and no create or delete.

### 3.4. Compile-time validation

A persist model is not compiled with its package. The file is compiled on its own, by the IDE while it is edited and by the persist tool each time it generates, from `bal build` or `bal persist generate`. The compiler plugin validates the file in both. When the persist tool compiles it, an error fails the generation and a warning is printed.

The compiler plugin acts only on a single-file project whose file is in a package's `persist` directory, `persist/<file>`, or in a named model's directory, `persist/<model>/<file>`, where the directory above `persist` holds `Ballerina.toml`. It does nothing in any other source.

| Condition | Code | Kind | Message |
|---|---|---|---|
| `@dataservice:Expose` is on a type that is not a record type | `DATASERVICE_101` | error | `the @dataservice:Expose annotation is allowed only on a record type in the persist model.` |
| `operations` names an action more than once | `DATASERVICE_102` | error | `duplicate operation '<value>' in the @dataservice:Expose annotation of the entity '<Entity>'. Remove the duplicate.` |
| A scope is empty or has whitespace | `DATASERVICE_110` | error | `invalid scope '<value>' in the @dataservice:Expose annotation of the entity '<Entity>'. A scope must be a non-empty string without whitespace.` |
| `scopes` names an action that is not in `operations` | `DATASERVICE_111` | error | `the @dataservice:Expose annotation of the entity '<Entity>' sets scopes for '<action>', which is not in 'operations'. Add it to 'operations', or remove its scopes.` |

`<value>` is the repeated operation or the scope as it is written, such as `dataservice:READ` or `"read"`. An action written as a member and as its string value is a duplicate, and each repeat is reported. An empty `operations` list or a value that is not an `Operation` is a type error that the compiler reports.

## 4. Field rules

### 4.1. Description

A field rule on a model field says whether a data service returns the field and accepts it on create and update.

### 4.2. Configuration

`ReadOnly` and `Internal` are constant annotations on a record field, of type `FieldRuleConfig`. `Immutable` is a constant annotation on a record field with no value.

| Field | Type | Default | Meaning |
|---|---|---|---|
| `value` | `anydata` | absent | The value the service sets the field to on create. When absent, the field is set to `()`. |

### 4.3. Behaviour

1. A field rule has this effect:

   | Annotation | Returned | Accepted on create | Accepted on update |
   |---|:-:|:-:|:-:|
   | `ReadOnly` | yes | no, ignored | no, ignored |
   | `Immutable` | yes | yes | no, rejected |
   | `Internal` | no | no, rejected | no, rejected |

2. On create, the service sets a `ReadOnly` or `Internal` field to the annotation's `value`, or to `()` without one.
3. A foreign key field declared with `@sql:Relation` takes the rules like any field.
4. A relation field takes only `Internal`, which withholds that direction of the relation. An `Internal` foreign key withholds both directions.

### 4.4. Compile-time validation

The compiler plugin checks the field rules of the files described in [3.4](#34-compile-time-validation).

| Condition | Code | Kind | Message |
|---|---|---|---|
| A field has more than one rule | `DATASERVICE_103` | error | `the field '<field>' of the entity '<Entity>' has more than one of @dataservice:ReadOnly, @dataservice:Immutable and @dataservice:Internal. Keep one.` |
| A key field has a rule, other than `ReadOnly` on a `@sql:Generated` key | `DATASERVICE_104` | error | `the key field '<field>' of the entity '<Entity>' cannot have @dataservice:<rule>.` |
| `ReadOnly` or `Internal` gives no `value` on a field that is neither nullable nor generated | `DATASERVICE_105` | error | `the field '<field>' of the entity '<Entity>' needs a 'value' in @dataservice:<rule>.` |
| `value` is not of the field's type | `DATASERVICE_106` | error | `the 'value' in @dataservice:<rule> of the field '<field>' of the entity '<Entity>' is not a '<type>'.` |
| `ReadOnly` or `Immutable` is on a relation field | `DATASERVICE_107` | error | `@dataservice:<rule> cannot be used on the relation field '<field>' of the entity '<Entity>'. Use it on the foreign key field, declared with @sql:Relation.` |
| The foreign key fields of one relation have different rules | `DATASERVICE_108` | error | `the foreign key fields of the relation '<relation>' of the entity '<Entity>' must have the same field rule.` |
| A rule affects only actions the entity does not allow | `DATASERVICE_109` | warning | `@dataservice:<rule> on the field '<field>' of the entity '<Entity>' has no effect. Remove it, or add '<actions>' to 'operations'.` |
| `ReadOnly` or `Internal` is on the foreign key of a one-to-one relation of an entity that allows `create` | `DATASERVICE_112` | error | `@dataservice:<rule> cannot be used on the field '<field>' of the entity '<Entity>', the foreign key of a one-to-one relation. Remove it.` |

A relation is one to one when neither of its relation fields is an array. `<actions>` names the actions the rule affects, joined by `' or '`: `update` for `Immutable`, `create` and `update` for `ReadOnly`, `read`, `create` and `update` for `Internal`, and `read` for `Internal` on a relation field.

## 5. Errors

### 5.1. Description

A data service answers every error with one error body, whose `code` names the error's category. Each protocol package maps a category to its own form, such as an HTTP status code.

### 5.2. Error body

The error body is the closed record `DataserviceError`, with the fields `code`, of type `ErrorCode`, and `message`, a `string`. A protocol package answers every error with it, including those its protocol module raises before the operation runs.

| Category | `code` | Raised when |
|---|---|---|
| Not found | `NOT_FOUND` | No record has the given key |
| Conflict | `CONFLICT` | A record with the key or a unique value already exists |
| Constraint violation | `CONSTRAINT_VIOLATION` | A write violates a foreign key |
| Invalid input | `INVALID_INPUT` | The input cannot be bound to the operation's type, a value is not in its format or breaks a constraint, a key is not a finite number, a query option is invalid, or a create holds too many records |
| Unauthenticated | `UNAUTHENTICATED` | With auth, the caller has no credential, or one that no provider accepts |
| Forbidden | `FORBIDDEN` | With auth, the caller holds no scope of the operation's action, or, for get related or a relation in `fields`, no `read` scope of the related entity |
| Internal | `INTERNAL` | Any other failure |

### 5.3. Persist errors

`toErrorBody` maps an error that the persist client returned to the error body, given the entity's name, the record's key and the operation's name. The message is written by `toErrorBody`, not taken from the error, because the SQL datastores put driver text, such as table and constraint names, in their error messages.

| Error | `code` | `message` |
|---|---|---|
| `persist:NotFoundError` | `NOT_FOUND` | `A record with the key '<key>' does not exist for the entity '<Entity>'.` |
| `persist:AlreadyExistsError` | `CONFLICT` | `A record that conflicts with an existing record of the entity '<Entity>' already exists.` |
| `persist:ConstraintViolationError` | `CONSTRAINT_VIOLATION` | `The operation violates a constraint of the entity '<Entity>'.` |
| Any other error | `INTERNAL` | `An internal error occurred.` |

`<key>` is the key text. For a constraint violation and an internal error, `toErrorBody` logs the error, with the entity's name and the operation's name, at the `ERROR` level. `toInternalErrorBody` logs an error in the same way and returns the `INTERNAL` body, whose message is `INTERNAL_MESSAGE`, whatever the error's category; a protocol package uses it for an error that its operation's responses do not include.

### 5.4. Keys

`checkFiniteKey` returns an `INVALID_INPUT` error body when a `float` value of a key is `NaN` or infinite, with the message `The key '<key>' of the entity '<Entity>' is not a finite number.`, where `<key>` is the key text, and `()` otherwise. A protocol calls it before it reads, updates or deletes a record by a key that has a `float` field.

### 5.5. Auth errors

- `toUnauthenticatedError` returns the `UNAUTHENTICATED` error body with the message `The request needs a valid credential.`
- `toNoScopeError` returns the `FORBIDDEN` error body with the message `The caller holds no scope that the operation needs.`
- `toForbiddenError` returns the `FORBIDDEN` error body with the message `The relation '<relation>' of the entity '<Entity>' needs a 'read' scope of the entity '<Target>'.`

A protocol package answers its protocol module's auth errors with `toUnauthenticatedError` and `toNoScopeError`. With auth, get related and a relation in `fields` require the entity's own `read` scopes. When those do not cover the related entity's, because the related entity's `read` list is not empty and the entity's list is empty or holds a scope the related entity's does not, the protocol checks the caller's credential against the related entity's `read` scopes, and answers with the `toForbiddenError` body when it holds none of them.

## 6. Value conversions

### 6.1. Description

The JSON form that Ballerina gives `byte[]` and the `time:*` record types does not suit a client: `time:Utc` is a tuple, the other `time:*` types are records, and `byte[]` is an array of numbers. A protocol that sends these values as JSON converts them with the functions of this section, so that every protocol uses the same formats.

### 6.2. Behaviour

Each `<type>ToString` function takes a value of the type and returns its string form. Each `<type>FromString` function takes a string and returns a value of the type, or a `ConversionError`.

| Type | To string | From string | Format |
|---|---|---|---|
| `byte[]` | `bytesToString` | `bytesFromString` | Base64, RFC 4648 standard alphabet, padded |
| `time:Date` | `dateToString` | `dateFromString` | `2024-01-02` |
| `time:TimeOfDay` | `timeOfDayToString` | `timeOfDayFromString` | `10:15:30` or `10:15:30.5` |
| `time:Civil` | `civilToString` | `civilFromString` | `2024-01-02T10:15:30`, without an offset |
| `time:Utc` | `utcToString` | `utcFromString` | `2024-01-02T10:15:30Z` |

- **`byte[]`:** the string must use the standard alphabet and padding. An unpadded string is a `ConversionError`.
- **`time:Date`:** written as `YYYY-MM-DD`. The string must be a valid calendar date.
- **`time:TimeOfDay`:** written as `HH:MM:SS`, followed by the fraction of a second only when it is not zero, in plain digits without trailing zeros. A missing `second` is written as `00`. The string must be `HH:MM:SS` with an optional fraction; `HH:MM` alone is a `ConversionError`.
- **`time:Civil`:** the date and the time joined by `T`. An offset in the value is not written. A string with an offset, including `Z`, is a `ConversionError`.
- **`time:Utc`:** written with `time:utcToString`. A string with the offset `Z` or `+hh:mm` is accepted and converted to UTC, as `time:utcFromString` does.

### 6.3. Errors

A `ConversionError` is a distinct error whose detail record, `ConversionErrorDetail`, holds `format`, the expected format, and optionally `'field`, the field the value was given for. Its message is `The value is not <format>.`

| Type | `format` |
|---|---|
| `byte[]` | `a base64 string` |
| `time:Date` | `an ISO 8601 date` |
| `time:TimeOfDay` | `an ISO 8601 time` |
| `time:Civil`, `time:Utc` | `an ISO 8601 date-time` |

A `ConversionError` for a value of a query option holds the field; see [8.3](#83-query-options).

## 7. Runtime configuration

### 7.1. Description

A generated service reads its runtime settings from one configurable record, `dataserviceConfig`, so a new setting needs no regeneration. This package defines the settings every protocol has and checks the page sizes.

### 7.2. Configuration

`Config` holds the settings every protocol has. A protocol package's configuration type includes it and adds its own fields, and it MAY give these fields other defaults.

| Field | Type | Default | Meaning |
|---|---|---|---|
| `port` | `int` | `9090` | The port the service listens on. |
| `pageSize` | `int` | `100` | The number of records in a page when the caller gives no size. It must be between `1` and `maxPageSize`. |
| `maxPageSize` | `int` | `1000` | The largest page, and the most records one create can hold. It must be at least `1`. |

### 7.3. Behaviour

1. A generated service checks its page sizes at startup with a module-level `check` on `toPageConfig`, given `pageSize` and `maxPageSize`. `toPageConfig` returns the page sizes as a `PageConfig`, a read-only record with the fields `size` and `maxSize`, or an error, so the program stops when a value is out of range.
2. `checkCreateSize` returns an `INVALID_INPUT` error body with the message `A create can hold at most <max> records.` when the number of records in a create is above `maxSize`, and `()` otherwise.

### 7.4. Errors

| Case | Message of the error that `toPageConfig` returns |
|---|---|
| `maxPageSize` below 1 | `The configurable value 'dataserviceConfig.maxPageSize' must be at least 1, found <value>.` |
| `pageSize` below 1 or above `maxPageSize` | `The configurable value 'dataserviceConfig.pageSize' must be between 1 and 'dataserviceConfig.maxPageSize' (<max>), found <value>.` |

## 8. Queries

### 8.1. Description

A data service reads records through the persist SQL client's `whereClause`, `orderByClause`, `limitClause` and `offsetClause`. This package validates the query options of a read and writes those clauses from the entity description.

### 8.2. Entity description

The generated service holds one entity description per exposed entity. Its shape is part of the contract, because generated code constructs it:

```ballerina
public enum Datastore {
    MYSQL,
    MSSQL,
    POSTGRESQL,
    H2
}

public enum FieldType {
    INT,
    FLOAT,
    DECIMAL,
    STRING,
    BOOLEAN,
    ENUM,
    BYTES,
    DATE,
    TIME_OF_DAY,
    CIVIL,
    UTC
}

public type Field record {|
    string name;
    string column;
    FieldType 'type;
    boolean nullable = false;
    boolean key = false;
    boolean generated = false;
|};

public type Entity readonly & record {|
    string name;
    string collection;
    string 'resource;
    Datastore datastore;
    Field[] fields;
    Relation[] relations = [];
|};

public type Relation record {|
    string 'field;
    boolean many;
    string[] fields;
    string[] targetFields;
    Entity target;
|};
```

1. `name` is the entity name, which the persist SQL client also uses as the table alias. `collection` is the entity's collection name in the service, such as `projectAssignments`, and `'resource` is its persist resource name, such as `projectassignments`.
2. `fields` holds, in model order, the fields that callers can see. A field with the `Internal` rule is left out, so no query option can use it. `column` is the field's column name.
3. `relations` holds the relations that callers can read: those whose related entity is also read by the service and that no `Internal` rule hides. `fields` and `targetFields` pair the link fields of the two entities. `many` is `true` for a to-many relation. `target` describes the related entity with its own fields and no relations, so every read is one hop.

### 8.3. Query options

`toQuery` validates the query options of get many, given the entity description, the page sizes, and the optional `filter`, `sort`, `size` and `offset`, and returns a `Query`. A `Query` holds the `whereClause`, `orderByClause`, `limitClause` and `offsetClause` to pass to the persist client, and the page size `size`.

1. **Filter:** a map from field name to a map from operator to value. Every condition must hold. A field of type `BYTES` cannot be filtered.

   | Operator | SQL | Field types |
   |---|---|---|
   | `eq`, `ne` | `=`, `<>` | every type but `BYTES` |
   | `lt`, `lte`, `gt`, `gte` | `<`, `<=`, `>`, `>=` | every type but `BYTES`, `BOOLEAN` and `ENUM` |
   | `anyOf` | `IN (...)`; an empty list matches no record | every type but `BYTES` |
   | `contains`, `startsWith` | `LIKE` with `ESCAPE '!'` | `STRING` |
   | `isNull` | `IS NULL` for `true`, `IS NOT NULL` for `false` | nullable fields |

   A value of a `DATE`, `TIME_OF_DAY`, `CIVIL` or `UTC` field is given in the string form of [6](#6-value-conversions). In `contains` and `startsWith`, `%`, `_` and `!` match themselves, as does `[` on MSSQL.
2. **Sort:** field names, each descending when it starts with `-`. The key fields not named are added in ascending order, so the order is total. Nulls sort last in ascending order and first in descending order: with `NULLS LAST` and `NULLS FIRST` on PostgreSQL and H2, and with a `CASE WHEN ... IS NULL` term on MySQL and MSSQL. An empty name is ignored.
3. **Size:** `size` of the page sizes when not given, and `maxSize` when larger. `limitClause` reads one row more than the page. `trimToPage` removes that row from the rows read and returns whether it was there, which tells whether records exist after the page.
4. **Offset:** `0` when not given, in which case `offsetClause` is empty.
5. **Identifiers:** written as `` `name` `` on MySQL, `[name]` on MSSQL and `"name"` on PostgreSQL and H2, with the quote character doubled inside a name, and qualified by the entity name.
6. **Values** are bound as parameters. Field and column names come only from the entity description.

For example, the filter `{"hiredOn": {"gte": "2024-01-01"}, "name": {"startsWith": "A"}}` with the sort `["-hiredOn"]` reads the employees hired on or after 2024-01-01 whose name starts with `A`, newest first and then by key.

### 8.4. Reading by keys

1. `toKeysQuery` returns the query that reads the records with the given keys, in key order, without a limit. A single key matches with `IN`; a composite key matches with `OR` over the key tuples.
2. A create reads its records back with it, and `orderByKeys` then puts them in the order of the given keys, in place. `orderByKeys` returns an error when a key has no record.

### 8.5. Fields

1. `checkFields` validates the `fields` option of a read against the entity description. Empty names are ignored. When relations are allowed, which is the default, `fields` can also name a relation, which includes the whole related record, or a field of the related entity as `<relation>.<field>`. A relation of the related entity, such as `department.employees`, cannot be named.
2. `selectFields` keeps the key fields and the named fields of a record, in model order. A record is read in full and then reduced with `selectFields`.

### 8.6. Relations

1. **Get related:** `toRelatedQuery` reads the records related to a record, given the record's link fields: the foreign key on the owning side, or the key on the other side. It takes the query options of [8.3](#83-query-options) on the related entity, and its errors name the related entity. A link with a nil value matches no record.
2. **Empty to-one:** `toRelatedNotFoundError` returns the `NOT_FOUND` error body `The record with the key '<key>' of the entity '<Entity>' has no '<relation>'.`, where `<key>` is the key text.
3. **Relations in `fields`:** `isIncluded` tells whether `fields` names a relation.
    1. For a to-one relation, `toIncludeQuery` reads the related records of a whole page with one query whose filter is `anyOf` their links, and `attachOne` adds each record's related record to its reduced record, or nil when there is none.
    2. For a to-many relation, `toIncludeQuery` reads the related records of one record, the page size plus one in key order. `trimToPage` cuts them to the page, and `attachMany` adds them as `{"items": [...], "hasMore": ...}`.
    3. The related records are reduced to the `<relation>.<field>` names, or kept whole when the relation is named alone.
4. **Composite links** match as `OR` over the link tuples.

### 8.7. Errors

`toQuery`, `toRelatedQuery` and `checkFields` return an `INVALID_INPUT` error body for an invalid option:

| Case | Message |
|---|---|
| An unknown field, or one that cannot be used for the option | `The field '<field>' of the entity '<Entity>' cannot be used in '<filter\|sort\|fields>'.` |
| An operator that does not apply to the field's type | `The operator '<operator>' cannot be used on the field '<field>' of the entity '<Entity>'.` |
| A field named more than once in `sort` | `The field '<field>' is named more than once in 'sort'.` |
| `fields` names no field | `'fields' must name at least one field.` |
| A size below 1 | `The page size must be at least 1.` |
| An offset below 0 | `The offset must be at least 0.` |
| An offset for which `offset + size` exceeds the largest integer | `The offset and the page size together exceed the largest integer.` |

A filter value that does not parse, or is not of the field's type, is returned as a `ConversionError` whose detail holds the field name, so that a protocol writes its own message for it.

## 9. Constraints

### 9.1. Description

A protocol whose wire types hold dates, times and `byte[]` values as strings cannot check the model's `ballerina/constraint` annotations on those fields when it binds the request. For example, `@constraint:Date {option: constraint:PAST}` on a `time:Date` field cannot be placed on the wire type's `string` field. The protocol converts the request to the persist type, which carries the annotations, and checks the result with `checkConstraints`.

### 9.2. Behaviour

`checkConstraints` validates a record against the `ballerina/constraint` annotations of its type, and returns `()` when every constraint holds.

### 9.3. Errors

When a constraint does not hold, `checkConstraints` returns an `INVALID_INPUT` error body for the first broken one, with the message `The field '<field>' of the entity '<Entity>' breaks its '<constraint>' constraint.`, where `<constraint>` is the name `ballerina/constraint` gives it, such as `maxLength` or `pastDate`.

## 10. Security considerations

- Query values are bound as SQL parameters. Field and column names in a query come only from the entity description, never from the request.
- An `Internal` field is left out of the entity description, so no query option can read, filter or sort on it.
- The error body never carries the persist client's error message, because the SQL datastores put driver text, such as table and constraint names, in it. Constraint violations and internal errors are logged instead.
- A page holds at most `maxPageSize` records, and a create at most `maxPageSize` records. An offset for which `offset + size` exceeds the largest integer is rejected.
- Scopes are checked only when the persist tool option `options.dataservice.auth` is `true`. Without it, every exposed operation is open to every caller.
